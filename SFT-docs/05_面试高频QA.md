## Agentic SFT TunningFactory — 面试高频 QA

> 本文档整理了围绕本项目及 LLM 微调领域的高频面试问题，结合项目源码进行深入解答。

---

### Q1: 请介绍一下这个项目的整体架构和你在其中的工作

**答**：

Agentic SFT TunningFactory 是基于开源 LLaMA-Factory (v0.5.3) 二次开发的阿里内部 LLM 微调训练框架。整体架构分为五层：

1. **用户入口层**：支持 CLI 命令行、YAML/JSON 配置文件、Web UI (Gradio)、API (FastAPI) 四种交互方式
2. **参数解析层** (`hparams/`)：基于 HuggingFace `HfArgumentParser` + `dataclass`，定义了 ModelArguments、DataArguments、FinetuningArguments 等五大参数类
3. **数据处理层** (`data/`)：完整的 Pipeline，从原始数据解析 → 格式对齐 → Tokenize → Packing → DataCollator
4. **模型加载层** (`model/`)：统一的模型加载、量化配置、适配器初始化（Full/Freeze/LoRA/ReFT）
5. **训练调度层** (`train/`)：根据 stage 分发到 PT/SFT/RM/PPO/DPO/KTO/Distill 七个训练 workflow

相比原版 LLaMA-Factory，主要扩展了：知识蒸馏训练、序列并行（Ulysses/Zigzag-Ring）、IFT Loss、Turbo 加速、以及阿里内部平台集成（星云 MDL、MOS 模型仓库、ODPS 数据源）。

### Q2: SFT 训练中，Label Masking 是怎么实现的？为什么要 mask prompt 部分？

**答**：

在 `data/processors/supervised.py` 的 `_encode_supervised_example()` 中实现。对于每一轮对话，将 prompt 部分的 labels 设为 `IGNORE_INDEX = -100`，只在 response 部分保留真实 token ID 作为 labels。

```
input_ids:  [BOS] [system] [user_query] [assistant_response] [EOS]
labels:     [-100] [-100]  [-100]       [assistant_response] [EOS]
```

PyTorch 的 `CrossEntropyLoss` 会自动忽略 label 为 -100 的位置，不计算这些位置的梯度。

**为什么要 mask prompt**：
- prompt 是用户输入，不是模型需要学习生成的内容
- 如果在 prompt 上也计算 loss，模型会学习"背诵"用户的问题，而不是学习如何回答
- 这与预训练的 Next Token Prediction 不同，SFT 的目标是让模型学会**根据指令生成高质量回复**

框架也支持 `--train_on_prompt` 参数，在某些场景下（如预训练式微调）可以在 prompt 上也计算 loss。

### Q3: LoRA 的原理是什么？项目中是如何实现的？

**答**：

**LoRA 原理**：对于预训练权重矩阵 W ∈ R^(d×k)，LoRA 不直接更新 W，而是学习一个低秩分解的增量 ΔW = BA，其中 B ∈ R^(d×r)，A ∈ R^(r×k)，r << min(d, k)。

前向传播：`h = Wx + BAx`，其中 W 冻结，只训练 B 和 A。

**项目实现**（`model/adapter.py` 的 `_setup_lora_tuning()`）：

1. **确定目标模块**：
   - `--lora_target all`：调用 `find_all_linear_modules()` 找到所有线性层
   - 指定模块名：如 `q_proj,v_proj`

2. **创建 LoRA 配置**：
   ```python
   lora_config = LoraConfig(
       task_type=TaskType.CAUSAL_LM,
       r=finetuning_args.lora_rank,           # 秩
       lora_alpha=finetuning_args.lora_alpha,  # 缩放因子
       lora_dropout=finetuning_args.lora_dropout,
       target_modules=target_modules,
       use_rslora=finetuning_args.use_rslora,
       use_dora=finetuning_args.use_dora,
   )
   model = get_peft_model(model, lora_config)
   ```

3. **多 Adapter 合并**：支持加载多个 LoRA adapter，先合并前面的，最后一个作为训练起点

**LoRA 的缩放**：实际增量为 `ΔW = (α/r) × BA`，其中 α 是 `lora_alpha`。默认 α = 2r，即缩放因子为 2。

### Q4: QLoRA 和 LoRA 有什么区别？

**答**：

QLoRA 在 LoRA 的基础上增加了**基础模型量化**：

| 维度 | LoRA | QLoRA |
|------|------|-------|
| 基础模型精度 | FP16/BF16 | 4-bit (NF4/FP4) |
| 可训练参数 | LoRA 矩阵 (FP16/BF16) | LoRA 矩阵 (FP16/BF16) |
| 显存占用 | 较大 | 显著减小 |
| 训练速度 | 较快 | 略慢（量化/反量化开销） |

项目中通过 `--quantization_bit 4` 启用 QLoRA。在 `model/patcher.py` 的 `configure_quantization()` 中配置 BitsAndBytes 量化：

```python
# NF4 量化配置
quantization_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_compute_dtype=compute_dtype,
    bnb_4bit_use_double_quant=model_args.double_quantization,
    bnb_4bit_quant_type=model_args.quantization_type,  # "nf4"
)
```

**NF4 (NormalFloat4)**：基于正态分布的 4-bit 量化，比 FP4 更适合正态分布的模型权重。

**双重量化 (Double Quantization)**：对量化常数本身再做一次量化，进一步节省显存（约 0.4 GB/billion 参数）。

### Q5: DeepSpeed ZeRO-2 和 ZeRO-3 的区别是什么？什么时候用哪个？

**答**：

| 维度 | ZeRO-2 | ZeRO-3 |
|------|--------|--------|
| 分片内容 | 优化器状态 + 梯度 | 优化器状态 + 梯度 + **模型参数** |
| 显存节省 | ~8x | ~N 倍 (N=GPU数) |
| 通信开销 | 较低 | 较高（需要 AllGather 参数） |
| 训练速度 | 较快 | 较慢 |
| 适用场景 | 7B~13B 全参数训练 | 13B~72B 大模型训练 |

**选择建议**：
- 7B 模型 + 8 卡 A100 → ZeRO-2 足够
- 13B 模型 + 8 卡 A100 → ZeRO-2 可能刚好，ZeRO-3 更稳妥
- 70B 模型 → 必须 ZeRO-3
- LoRA 训练 → 通常不需要 DeepSpeed，DDP 即可

项目中的配置差异主要在 `zero_optimization.stage` 字段（2 vs 3），以及 ZeRO-3 额外的 `stage3_prefetch_bucket_size`、`stage3_param_persistence_threshold` 等参数。

### Q6: Packing 是什么？为什么需要 Neat Packing？

**答**：

**Packing**：将多个短样本拼接到一个 `cutoff_len` 长度的序列中，避免大量 padding 浪费计算资源。

```
Without Packing:
[sample1 ........... PAD PAD PAD PAD PAD PAD]  ← 大量 padding 浪费
[sample2 ... PAD PAD PAD PAD PAD PAD PAD PAD]

With Packing:
[sample1 ........... sample2 ... sample3 ..]  ← 紧密拼接，利用率高
```

项目使用**贪心背包算法** (`greedy_knapsack()`) 最优化装箱。

**Neat Packing 的必要性**：普通 Packing 中，不同样本的 token 之间会产生注意力交互（跨样本注意力泄露），导致训练信号不纯。

Neat Packing 使用 **Block-Diagonal 4D Attention Mask**：

```
attention_mask (neat_packing):
[
  [o, x, x, x, x, x],    ← sample 1 只看 sample 1
  [o, o, x, x, x, x],
  [x, x, o, x, x, x],    ← sample 2 只看 sample 2
  [x, x, o, o, x, x],
  [x, x, o, o, o, x],
  [x, x, x, x, x, x],    ← padding
]
```

在 `data/collator.py` 的 `prepare_4d_attention_mask()` 中实现：通过 attention_mask 中的不同整数值标识不同样本（1, 2, 3...），然后构建 Block-Diagonal 的 4D mask。

### Q7: DPO 和 PPO 的区别是什么？各有什么优缺点？

**答**：

| 维度 | PPO | DPO |
|------|-----|-----|
| **是否需要奖励模型** | 需要单独训练 RM | 不需要 |
| **训练复杂度** | 高（4 个模型同时运行） | 低（2 个模型） |
| **显存需求** | 非常大 | 较大 |
| **训练稳定性** | 较差，超参敏感 | 较好 |
| **理论基础** | 强化学习 | 监督学习 |
| **数据需求** | 只需 prompt | 需要 chosen/rejected 配对 |
| **效果** | 理论上限更高 | 实践中通常足够好 |

**PPO 的训练循环**：
1. Actor 生成 response → 2. RM 打分 → 3. 计算 KL 惩罚 → 4. GAE 优势估计 → 5. PPO Clip 更新

**DPO 的核心思想**：将 RM + RL 合并为一个监督学习问题，直接从偏好数据学习策略。损失函数：
```
L_DPO = -log σ(β · (log π_θ(y_w|x)/π_ref(y_w|x) - log π_θ(y_l|x)/π_ref(y_l|x)))
```

项目中 DPO 还支持多种变体：SimPO（无需参考模型）、ORPO（无需参考模型）、IPO、IFT 等。

### Q8: 知识蒸馏的原理是什么？项目中是怎么实现的？

**答**：

**原理**：让 Student 模型不仅学习 ground truth 的 hard labels，还学习 Teacher 模型输出的 soft logits 分布。soft logits 包含了类别间的相似性信息（"暗知识"）。

**损失函数**：
```
L = (1 - α) · CE(student_logits, labels) + α · KL(softmax(student_logits/T), softmax(teacher_logits/T)) · T²
```

**项目实现**（`train/distill/`）：

1. **双模型加载**：同时加载 Student 和 Teacher 模型，Teacher 模型冻结
2. **双 Template**：Student 和 Teacher 可以使用不同的 prompt template（`--template` vs `--teacher_template`）
3. **DistillDataCollator**：同时为两个模型准备输入，输出 `student_features` 和 `teacher_features`
4. **多种 KD 目标**：支持 forward_kl、reverse_kl、adaptive_kl、js_divergence 等

**Forward KL vs Reverse KL**：
- Forward KL (`KL(P_teacher || P_student)`)：Mode-covering，Student 尝试覆盖 Teacher 的所有模式
- Reverse KL (`KL(P_student || P_teacher)`)：Mode-seeking，Student 集中在 Teacher 的高概率区域

### Q9: FlashAttention 的原理是什么？为什么能加速？

**答**：

**标准 Attention 的瓶颈**：不是计算量，而是**内存访问**。标准实现需要将 N×N 的注意力矩阵写入 HBM（高带宽内存），然后再读回来做 softmax 和加权求和。HBM 的带宽远低于 GPU 计算单元的吞吐量。

**FlashAttention 的核心思想**：IO-aware Tiling
1. 将 Q、K、V 分成小块（tiles）
2. 在 SRAM（片上内存，带宽远高于 HBM）中计算注意力
3. 使用 online softmax 算法，避免存储完整的 N×N 矩阵
4. 通过分块累积的方式得到最终结果

**效果**：
- 显存：从 O(N²) 降低到 O(N)
- 速度：2-4x 加速
- 精确计算，无近似

项目中通过 `--flash_attn fa2` 启用，在 `model/model_utils/attention.py` 的 `configure_attn_implementation()` 中配置。

### Q10: Prompt Template 的作用是什么？不同模型为什么需要不同的 Template？

**答**：

**作用**：将用户的自然语言输入转换为模型预训练时使用的特定格式。如果格式不匹配，模型无法正确理解输入的结构（哪部分是系统提示、哪部分是用户问题、哪部分是期望回复）。

**不同模型的 Template 差异**：

```
# Qwen 格式
<|im_start|>system\n{system}<|im_end|>\n<|im_start|>user\n{query}<|im_end|>\n<|im_start|>assistant\n

# LLaMA-2 格式
[INST] <<SYS>>\n{system}\n<</SYS>>\n\n{query} [/INST]

# ChatGLM3 格式
<|system|>\n{system}<|user|>\n{query}<|assistant|>\n
```

项目在 `data/template.py` 中定义了 Template 类，每个模型注册自己的格式化器。`constants.py` 中通过 `register_model_group()` 将模型与 Template 绑定。

**错误 Template 的后果**：
- 模型无法识别指令边界，输出混乱
- Loss 不下降或下降极慢
- 生成时无法正确停止（缺少正确的 stop token）

### Q11: 梯度检查点 (Gradient Checkpointing) 的原理是什么？

**答**：

**问题**：反向传播需要前向传播时保存的中间激活值来计算梯度。对于深层网络，这些激活值占用大量显存。

**梯度检查点的策略**：
- 前向传播时**不保存**中间激活值（只保存少数检查点层的激活）
- 反向传播时，从最近的检查点**重新计算**需要的激活值

**权衡**：
- 显存降低约 60%（只保存 √N 个检查点层的激活，N 为总层数）
- 训练时间增加约 30%（需要额外的前向计算）

项目中默认启用梯度检查点，通过 `model/model_utils/checkpointing.py` 的 `prepare_model_for_training()` 配置。可通过 `--disable_gradient_checkpointing` 禁用。

### Q12: 序列并行 (Sequence Parallelism) 和数据并行、模型并行有什么区别？

**答**：

| 并行方式 | 切分维度 | 解决的问题 | 通信模式 |
|---------|---------|-----------|---------|
| **数据并行 (DP)** | Batch 维度 | 加速训练 | AllReduce 梯度 |
| **模型并行 (TP)** | 模型参数维度 | 单卡放不下模型 | AllReduce 激活 |
| **流水线并行 (PP)** | 模型层维度 | 单卡放不下模型 | 点对点传输 |
| **序列并行 (SP)** | 序列长度维度 | 单卡放不下长序列 | AllToAll / Ring |

**序列并行的必要性**：注意力机制的显存与序列长度的平方成正比。当序列长度从 4K 增加到 128K 时，注意力显存增加 1024 倍。

项目支持两种 SP 模式：
- **Ulysses**：均匀切分序列，AllToAll 通信交换 Q/K/V 的注意力头
- **Zigzag-Ring**：交错切分序列，Ring 通信传递 K/V

### Q13: 项目中的 IFT Loss 是什么？

**答**：

IFT (Implicit Future Training) 是项目中实现的一种增强损失函数，在 `train/sft/trainer.py` 的 `compute_ift_loss()` 中实现。

**核心思想**：在标准 SFT 中，模型只看到 ground truth 的前缀来预测下一个 token。IFT 让模型也看到自己的**贪心预测结果**（可能是错误的），然后学习在这种"被污染"的上下文中仍然能生成正确的 token。

**实现步骤**：
1. 用当前模型做一次前向传播，得到贪心预测 `tokens_further`
2. 将 ground truth 和贪心预测按比例混合：`(1-λ) × gt_embeds + λ × pred_embeds`
3. 用混合后的 embedding 再做一次前向传播
4. 使用**累积权重** (`get_cumsum_weight()`) 对 loss 进行加权，让后面的 token 获得更大的权重

**效果**：提升模型在推理时的鲁棒性，减少 exposure bias（训练时看 ground truth，推理时看自己的预测）。

### Q14: 多模态微调是怎么实现的？

**答**：

项目通过 **Plugin 机制** (`data/mm_plugin.py`) 支持多模态：

1. **数据层**：在文本中使用占位符 `<image>`/`<video>`/`<audio>` 标记多模态内容位置
2. **对齐层**：`aligner.py` 将多模态文件路径转换为绝对路径
3. **Collator 层**：`MultiModalDataCollatorForSeq2Seq` 在 batch 组装时：
   - 调用 `process_single_mm_input()` 提取多模态特征
   - 将占位符 token 替换为实际的视觉/音频 token
4. **模型层**：通过 `patcher.py` 的 `configure_visual_model()` 和 `autocast_projector_dtype()` 配置视觉编码器

**支持的多模态模型**：Qwen-VL、Qwen2-VL、Qwen2.5-Omni、InternVL2、MiniCPM-V/O、DeepSeek-VL2、GLM-4V 等。

**Freeze 视觉塔**：多模态微调时通常冻结视觉编码器，只训练语言模型和投影层：
```bash
--finetuning_type freeze --freeze_module_prefix vision_tower
```

### Q15: 如何评估微调后的模型效果？

**答**：

项目提供三个层次的评估：

1. **训练指标**：Loss 曲线（`--plot_loss`）、eval_loss、训练中的 accuracy
2. **生成式评估**：`--predict_with_generate`，计算 BLEU、ROUGE 等指标
3. **基准评估**：MMLU（英文 57 科目）、C-Eval（中文 52 科目）、CMMLU（中文 67 科目），使用 few-shot 评估

**评估命令**：
```bash
python src/evaluate.py \
    --model_name_or_path output/merged_model \
    --template qwen \
    --task ceval \
    --n_shot 5 \
    --batch_size 4
```

**过拟合判断**：
- train_loss 持续下降但 eval_loss 上升 → 过拟合
- 解决方案：减少训练轮数、增加数据量、增大 dropout、使用 early stopping

### Q16: 项目中的 Callback 机制是怎么工作的？

**答**：

基于 HuggingFace Trainer 的 `TrainerCallback` 接口，在训练的不同阶段插入自定义逻辑：

```python
class TrainerCallback:
    def on_train_begin(...)     # 训练开始
    def on_train_end(...)       # 训练结束
    def on_epoch_begin(...)     # 每个 epoch 开始
    def on_step_begin(...)      # 每个 step 开始
    def on_step_end(...)        # 每个 step 结束
    def on_log(...)             # 日志记录时
    def on_evaluate(...)        # 评估时
    def on_save(...)            # 保存 checkpoint 时
```

项目中的关键 Callback：
- **PushToMosCallback**：在 `on_save` 时将 checkpoint 上传到 MOS
- **InteractiveCkptCallback**：支持训练过程中动态触发 checkpoint 保存
- **CustomEarlyStoppingCallback**：在 `on_evaluate` 后检查指标是否改善，决定是否早停
- **DynamicInterleaveCallBack**：在 `on_epoch_begin` 时动态调整多数据集的采样概率

### Q17: 如何处理训练中的 Loss NaN 问题？

**答**：

**常见原因与解决方案**：

1. **FP16 溢出**：
   - 切换到 BF16（`--bf16`），BF16 的动态范围更大
   - 调整 loss scaling 参数

2. **学习率过大**：
   - 减小学习率
   - 使用 warmup（`--warmup_ratio 0.1`）

3. **数据问题**：
   - 检查数据中是否有异常值
   - 检查 tokenize 后是否有空序列

4. **梯度爆炸**：
   - 启用梯度裁剪（`--max_grad_norm 1.0`，默认已启用）

5. **量化模型不稳定**：
   - QLoRA 训练时确保使用 NF4 而非 FP4
   - 启用双重量化

### Q18: DoRA 和标准 LoRA 有什么区别？

**答**：

**DoRA (Weight-Decomposed LoRA)** 将预训练权重分解为**方向**和**大小**两个分量：

```
W = m · (W₀ + BA) / ||W₀ + BA||
```

其中 `m` 是可学习的大小向量，`W₀ + BA` 的归一化结果表示方向。

**与标准 LoRA 的区别**：
- 标准 LoRA 同时修改方向和大小，两者耦合
- DoRA 解耦方向和大小的学习，更接近全参数微调的更新模式
- DoRA 通常能在相同 rank 下获得更好的效果

项目中通过 `--use_dora` 参数启用，在 `adapter.py` 中传递给 PEFT 的 `LoraConfig`。

### Q19: 训练大模型时，显存都被什么占用了？

**答**：

以 7B FP16 模型 + Adam 优化器为例：

| 组成部分 | 计算方式 | 显存占用 |
|---------|---------|---------|
| 模型参数 (FP16) | 7B × 2 bytes | 14 GB |
| 梯度 (FP16) | 7B × 2 bytes | 14 GB |
| Adam 一阶矩 (FP32) | 7B × 4 bytes | 28 GB |
| Adam 二阶矩 (FP32) | 7B × 4 bytes | 28 GB |
| Adam 参数副本 (FP32) | 7B × 4 bytes | 28 GB |
| 激活值 | 取决于 batch size 和序列长度 | 变化 |
| **总计（不含激活）** | | **~112 GB** |

**优化手段**：
- **LoRA**：只训练 ~0.1% 参数，梯度和优化器状态大幅减少
- **QLoRA**：模型参数从 14 GB 降到 ~3.5 GB (4-bit)
- **ZeRO**：将优化器状态/梯度/参数分片到多卡
- **梯度检查点**：用重计算换激活值显存
- **混合精度**：减少激活值的精度

### Q20: 项目中如何保证训练的可复现性？

**答**：

1. **随机种子**：`--seed 42`（默认），控制数据 shuffle、dropout、初始化等
2. **完全确定性**：`--full_determinism`，禁用所有非确定性操作（会降低性能）
3. **数据顺序**：固定数据加载顺序和 shuffle seed
4. **Checkpoint 恢复**：`--resume_from_checkpoint`，从断点恢复训练状态
5. **配置记录**：训练参数自动保存到 `training_args.bin` 和 `trainer_log.jsonl`

注意：DeepSpeed ZeRO-3 和序列并行可能引入非确定性，完全可复现需要使用 ZeRO-2 + `--full_determinism`。
