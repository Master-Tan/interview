## ROLL 面试高频 QA

### Q1: ROLL 是什么？解决了什么问题？

**A**: ROLL（Reinforcement Learning Optimization for Large-Scale Learning）是阿里巴巴开发的大模型强化学习训练框架。它解决的核心问题是：**如何高效、灵活地对大语言模型进行 RL 后训练（Post-Training）**。

传统的 LLM RL 训练面临以下挑战：
1. **系统复杂度高**: RL 训练涉及多个模型角色（Actor/Critic/Reference/Reward），需要协调推理、训练、奖励计算等多个阶段
2. **资源利用率低**: 推理和训练交替执行，GPU 存在大量空闲时间
3. **扩展性差**: 从单机到多机集群的扩展需要大量工程改造
4. **算法迭代慢**: 不同 RL 算法的实现缺乏统一抽象

ROLL 通过 **Ray-based 多角色分布式架构 + Strategy 策略抽象 + 配置驱动** 的设计，提供了一站式的解决方案。

---

### Q2: ROLL 的整体架构是怎样的？

**A**: ROLL 采用四层架构：

1. **Pipeline Layer**: 定义训练流程（RLVR/Agentic/Distill/DPO/SFT），每种 Pipeline 继承自 `BasePipeline`
2. **Scheduler Layer**: 调度数据流和异步操作（GenerateScheduler/RolloutScheduler/RewardScheduler）
3. **Executor Layer**: 基于 Ray Actor 的分布式执行引擎（Cluster → Worker → Strategy）
4. **Backend Layer**: 底层训练/推理引擎（DeepSpeed/Megatron/vLLM/SGLang）

核心设计思想是**关注点分离**：Pipeline 关注训练逻辑，Scheduler 关注调度优化，Strategy 关注后端适配。

---

### Q3: ROLL 中的 Cluster、Worker、Strategy 分别是什么关系？

**A**:

- **Worker** 是最基本的执行单元，每个 Worker 是一个 Ray Actor，运行在指定的 GPU 上。Worker 持有一个 Strategy 实例，通过 Strategy 执行具体的训练/推理操作。

- **Cluster** 管理一组 Worker，是 Pipeline 与 Worker 之间的桥梁。Cluster 通过 `_bind_worker_method()` 实现方法代理——Worker 上标记了 `@register(dispatch_mode=...)` 的方法会被自动绑定到 Cluster 上，Pipeline 可以直接调用 `cluster.generate(data)` 而无需关心底层的分发逻辑。

- **Strategy** 是训练/推理后端的抽象层。`InferenceStrategy` 定义了推理接口（generate/forward_step），`TrainStrategy` 继承并扩展了训练接口（train_step/save_checkpoint）。不同的后端（DeepSpeed/Megatron/vLLM/SGLang）实现各自的 Strategy。

**调用链**: `Pipeline → Cluster → Worker → Strategy → 底层引擎`

---

### Q4: DataProto 是什么？为什么需要它？

**A**: `DataProto` 是 ROLL 中所有模块间数据交换的标准协议，包含三个部分：

```python
@dataclass
class DataProto:
    batch: TensorDict          # 张量数据（input_ids, attention_mask 等）
    non_tensor_batch: Dict     # 非张量数据（tag, ground_truth 等）
    meta_info: Dict            # 元信息（metrics, generation_config 等）
```

**设计原因**:
1. **统一接口**: 所有模块（生成、训练、奖励计算）使用相同的数据格式，避免格式转换
2. **高效传输**: 基于 PyTorch TensorDict，自定义序列化优化 Ray RPC 传输
3. **灵活操作**: 支持切片、索引、拼接、padding 等操作，像操作单个 Tensor 一样操作整个 batch
4. **混合数据**: 同时管理张量和非张量数据（如字符串类型的 ground_truth）

### Q5: RLVR 和传统 RLHF 有什么区别？

**A**:

| 维度 | RLHF | RLVR |
|------|------|------|
| **奖励来源** | 训练的 Reward Model | 规则验证器（数学答案匹配、代码执行等） |
| **奖励质量** | 受 RM 质量限制，可能有偏差 | 精确的二值奖励（对/错），无偏差 |
| **适用场景** | 开放式对话、偏好对齐 | 可验证任务（数学、代码、指令遵循） |
| **训练稳定性** | 较差（RM 噪声大） | 较好（奖励信号清晰） |
| **是否需要 Critic** | 通常需要 | 可以不需要（使用 Reinforce++/GRPO） |

ROLL 的 RLVR Pipeline 支持多种 Reward Worker（Math Rule、Code Sandbox、LLM Judge 等），可以灵活组合。

### Q6: GRPO 和 PPO 的核心区别是什么？

**A**:

**PPO（Proximal Policy Optimization）**:
- 需要 Critic 网络估计 Value 函数
- 使用 GAE（Generalized Advantage Estimation）计算 Advantage
- 训练开销大（需要额外的 Critic 模型）
- 公式: `L = -min(ratio * A, clip(ratio, 1±ε) * A)`

**GRPO（Group Relative Policy Optimization）**:
- **不需要 Critic 网络**
- 对同一 prompt 的 K 个 response 进行组内标准化作为 Advantage
- 训练开销小（省去 Critic 的计算和显存）
- 公式: `A_i = (R_i - mean(R)) / std(R)`

**GRPO 的优势**: 在 RLVR 场景下，由于奖励信号清晰（对/错），GRPO 的组内标准化已经足够提供好的梯度信号，不需要额外的 Critic 网络。这大大降低了训练的资源需求。

### Q7: ROLL 如何实现 GPU 时分复用？

**A**: 当 Actor Train 和 Actor Infer 共享 GPU（colocated 部署）时，ROLL 通过 **offload/reload 机制** 实现时分复用：

```
推理阶段:
  Actor Train 参数 → offload 到 CPU
  Actor Infer 参数 → reload 到 GPU
  执行推理生成...

训练阶段:
  Actor Infer 参数 → offload 到 CPU
  Actor Train 参数 + 优化器状态 → reload 到 GPU
  执行策略梯度更新...
```

**实现细节**:
- `offload_states()`: 将模型参数、优化器状态、梯度缓冲区移到 CPU
- `load_states()`: 将状态从 CPU 移回 GPU
- 通过 `state_offload_manager` 上下文管理器自动管理 offload/reload
- 支持选择性 offload（只 offload 模型参数，保留优化器状态在 CPU）

**检测逻辑**: `is_colocated()` 函数检查训练和推理的 `device_mapping` 是否有重叠，自动决定是否启用时分复用。

### Q8: ROLL 的模型参数同步是如何实现的？

**A**: 通过 `ModelUpdateGroup` 实现训练集群到推理集群的参数同步：

1. **建立通信组**: 为每个 PP stage 建立独立的 NCCL 通信组，Train Worker 作为 sender，Infer Worker 作为 receiver
2. **参数广播**: 支持两种模式：
   - **逐参数广播**: 遍历模型参数，逐个 broadcast
   - **Bucket 批量广播**: 将多个参数打包到 bucket 中一次性传输（更高效）
3. **频率控制**: 通过 `model_update_frequency` 控制同步频率（默认每步同步）

**关键优化**: 当 Megatron 使用 PP 并行时，不同 PP stage 的参数分布在不同的 Worker 上，ROLL 会为每个 PP stage 建立独立的通信组，确保参数正确同步。

### Q9: ROLL 如何支持多任务 RL 训练？

**A**: ROLL 通过 **tag 机制 + domain_interleave_probs** 实现多任务混合训练：

1. **数据标记**: 每条数据携带 `tag` 标识其所属任务域（如 math_rule、code_sandbox）
2. **采样控制**: `domain_interleave_probs` 控制各任务域的采样比例
3. **奖励路由**: `RewardScheduler` 根据 `tag` 将数据路由到对应的 Reward Worker
4. **指标追踪**: 按 domain 分组追踪奖励和正确率

```yaml
domain_interleave_probs:
  math_rule: 0.4      # 40% 数学
  code_sandbox: 0.3    # 30% 代码
  llm_judge: 0.3       # 30% 通用
```

**优势**: 不同任务可以使用不同的 Reward Worker（规则验证、代码沙箱、LLM 评判），灵活组合。

### Q10: Agentic RL 和 RLVR 的核心区别是什么？

**A**:

| 维度 | RLVR | Agentic RL |
|------|------|-----------|
| **交互方式** | 单轮（prompt → response） | 多轮（prompt → action → observation → action → ...） |
| **Rollout** | GenerateScheduler（一次性生成） | RolloutScheduler（多轮交互） |
| **环境** | 无环境（直接验证答案） | 有环境（FrozenLake、Sokoban、WebShop 等） |
| **奖励** | 最终奖励（对/错） | 可以是 step-level 或 trajectory-level |
| **训练范式** | TrajectoryWise | TrajectoryWise（StarPO）或 StepWise（GiGPO） |
| **异步** | Sample-level 异步 | Environment-level 异步 |

**Agentic RL 的关键组件**:
- **EnvManager**: 管理环境的生命周期和多轮交互
- **RolloutScheduler**: 协调多个环境的异步 rollout
- **GroupQueue**: 管理环境组，支持冗余生成和过滤

### Q11: ROLL 支持哪些 RL 算法？各自适用什么场景？

**A**:

| 算法 | 是否需要 Critic | 适用场景 | 核心思想 |
|------|----------------|---------|---------|
| **PPO** | ✅ | 通用 RL | Clip 约束 + GAE |
| **GRPO** | ❌ | RLVR | Group 内相对标准化 |
| **Reinforce++** | ❌ | RLVR | Running mean 基线 |
| **TOPR** | ❌ | RLVR | 正负样本不同权重 |
| **RAFT++** | ❌ | RLVR | 只用高奖励样本训练 |
| **GSPO** | ❌ | RLVR | Group 内最佳/最差对比 |
| **GiGPO** | ❌ | Agentic | Step-level 优势 |
| **StarPO** | ❌ | Agentic | Trajectory-level 优势 |
| **LitePPO** | ✅(mini) | 通用 RL | 小型 Critic 降低开销 |
| **RewardFL** | ❌ | 扩散模型 | Reward 微调 |

### Q12: Megatron 5D 并行具体指什么？

**A**: Megatron 支持 5 个维度的并行：

1. **DP（Data Parallel）**: 数据并行，每个 DP rank 处理不同的数据子集
2. **TP（Tensor Parallel）**: 张量并行，将模型层内的权重矩阵按列/行切分到多个 GPU
3. **PP（Pipeline Parallel）**: 流水线并行，将模型的不同层分配到不同 GPU，通过 micro-batch 流水线执行
4. **CP（Context Parallel）**: 上下文并行，将序列长度切分到多个 GPU（通过 Ulysses Attention 实现）
5. **EP（Expert Parallel）**: 专家并行，用于 MoE 模型，将不同的 Expert 分配到不同 GPU

**DP Size 自动计算**: `dp_size = total_gpus / (tp_size × pp_size × ep_size)`

**ROLL 中的配置**:
```yaml
strategy_config:
  tensor_model_parallel_size: 2   # TP=2
  pipeline_model_parallel_size: 2  # PP=2
  expert_model_parallel_size: 4   # EP=4（MoE）
```

### Q13: vLLM 和 SGLang 在 ROLL 中的角色是什么？

**A**: vLLM 和 SGLang 都是高性能 LLM 推理引擎，在 ROLL 中用作 **Actor Infer 的推理后端**，负责 Rollout 阶段的 response 生成。

**vLLM 特性**:
- PagedAttention：高效的 KV Cache 管理
- Continuous Batching：动态批处理
- 支持 TP 多卡推理
- 支持 FP8 量化推理

**SGLang 特性**:
- RadixAttention：基于前缀树的 KV Cache 复用
- 在某些场景下性能优于 vLLM
- 支持结构化生成

**选择建议**:
- 默认使用 vLLM（生态更成熟）
- 如果有大量共享前缀的场景，考虑 SGLang
- MoE 模型推荐 SGLang

---

### Q14: ROLL 如何处理训练中的长尾延迟问题？

**A**: ROLL 通过多层次的优化来解决长尾延迟：

1. **Sample-level 异步 Rollout**（`generate_opt_level=1`）：逐条分发请求，完成一条立即回调，不等待最慢的样本
2. **Dynamic Batching**: 按序列长度分组，减少 padding 浪费
3. **Sequence Packing**: 将多个短序列打包到一个长序列中
4. **Remove Padding**: 移除尾部 padding token
5. **RollPacker**（论文 arXiv:2509.21009）: 专门针对 RL 训练中 rollout 长度分布不均的优化

### Q15: ROLL 的 Strategy 工厂模式是如何设计的？

**A**: ROLL 使用**延迟导入 + 工厂模式**来创建 Strategy：

```python
def create_strategy(worker):
    strategy_name = worker.worker_config.strategy_args.strategy_name
    if strategy_name == "vllm":
        from roll.distributed.strategy.vllm_strategy import VllmStrategy
        return VllmStrategy(worker)
    elif strategy_name == "megatron_train":
        from roll.distributed.strategy.megatron_strategy import MegatronTrainStrategy
        return MegatronTrainStrategy(worker)
    # ...
```

**延迟导入的原因**: 避免 CUDA 提前初始化。在 Ray Actor 中，Worker 创建时还不知道自己会运行在哪个 GPU 上，如果提前 import 了 CUDA 相关的库，可能导致 CUDA context 在错误的 GPU 上初始化。

### Q16: ROLL 中的 Dispatch 模式有哪些？

**A**: Dispatch 模式定义了 Cluster 如何将请求分发到 Worker：

| 模式 | 说明 | 使用场景 |
|------|------|---------|
| `ONE_TO_ALL` | 广播到所有 Worker | offload_states、load_states |
| `DP_MP_COMPUTE` | 按 DP 维度分发数据，MP 维度内复制 | compute_log_probs、generate |
| `MEGATRON_PP_COMPUTE` | Megatron PP 流水线分发 | Megatron 训练/推理 |

实现原理：Worker 方法通过 `@register(dispatch_mode=Dispatch.DP_MP_COMPUTE)` 装饰器标记分发模式，Cluster 在 `_bind_worker_method()` 时自动绑定对应的分发和收集函数。

### Q17: ROLL 如何实现断点续训？

**A**: ROLL 的断点续训机制包含三个层面：

1. **模型权重**: 各 Cluster 通过 Strategy 保存/加载模型权重和优化器状态
2. **Pipeline 状态**: `WorkerState` 保存训练步数、日志历史、随机数状态
3. **远程存储**: `CheckpointManager` 支持将检查点上传到远程存储（OSS/文件系统）

```python
# 恢复流程
if resume_from_checkpoint:
    # 1. 下载检查点
    ckpt_path = download_model(resume_from_checkpoint)
    # 2. 恢复 Pipeline 状态
    state = WorkerState.load_from_json(ckpt_path)
    # 3. 跳过已完成的 step
    for step in range(max_steps):
        if step <= state.step:
            continue
        # 正常训练...
```

### Q19: 什么是 Advantage Whitening？为什么需要它？

**A**: Advantage Whitening（优势白化）是对计算出的 advantage 值进行标准化处理：

```python
advantages = (advantages - mean(advantages)) / (std(advantages) + eps)
```

**为什么需要**:
1. **稳定训练**: 不同 batch 的 advantage 量级可能差异很大，白化后量级一致
2. **梯度稳定**: 避免 advantage 过大导致梯度爆炸，或过小导致梯度消失
3. **与 clip 配合**: PPO 的 clip 机制假设 advantage 在合理范围内，白化确保这一点

**注意**: 白化会改变 advantage 的符号分布，可能将原本全正的 advantage 变为有正有负。在 RLVR 场景下（奖励为 0/1），这意味着即使所有 response 都正确，白化后也会有"负"的 advantage。

### Q20: ROLL 中的 Running Moments 是什么？

**A**: `RunningMoments` 是一个在线统计工具，使用 Welford 算法增量计算均值和标准差：

```python
class RunningMoments:
    def update(self, xs):
        # 增量更新均值和方差
        delta = xs_mean - self.mean
        self.mean += delta * xs_count / tot_count
        self.var = (old_sum + new_sum) / tot_count
        self.std = sqrt(self.var)
```

**用途**:
1. **Reward Normalization**: 跨 batch 标准化奖励值
2. **Reinforce++ Baseline**: 使用 running mean 作为 baseline
3. **Advantage Estimation**: 在某些算法中用于估计 advantage 的基线

**优势**: 不需要存储所有历史数据，只需维护均值、方差和计数，内存开销为 O(1)。
