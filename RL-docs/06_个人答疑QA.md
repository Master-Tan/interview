### Q1: 我想在 ROLL 上训练自己的模型，最小化需要准备什么？

**A**: 你需要准备以下内容：

1. **模型**: HuggingFace 格式的预训练模型（本地路径或 ModelScope/HuggingFace Hub ID）
2. **数据**: jsonl 格式的训练数据，每条数据包含：
   - `messages`: 对话格式的 prompt（`[{"role": "user", "content": "..."}]`）
   - `ground_truth`: 标准答案（用于 Reward 计算）
   - `data_source` / `tag`: 任务域标识
3. **YAML 配置文件**: 参考 `examples/` 目录下的模板，修改以下关键字段：
   - `pretrain`: 模型路径
   - `data_args.file_name`: 数据文件路径
   - `device_mapping`: GPU 分配
   - `strategy_args`: 训练/推理后端选择
4. **环境**: 安装 ROLL 及其依赖（参考 `requirements_torch280_sglang.txt`）

**最简启动**:
```bash
# 8 GPU 单节点，Qwen2.5-7B RLVR 训练
bash examples/qwen2.5-7B-rlvr_megatron/run_rlvr_pipeline.sh
```

### Q2: 如何为自己的任务编写自定义 Reward Worker？

**A**: 继承 `BaseRewardWorker` 并实现 `compute_reward` 方法：

```python
# 文件: roll/pipeline/rlvr/rewards/my_reward_worker.py
from roll.pipeline.rlvr.rewards.base_reward_worker import BaseRewardWorker

class MyRewardWorker(BaseRewardWorker):
    def compute_reward(self, data):
        """
        data 包含:
        - data.batch["input_ids"]: 完整序列的 token ids
        - data.non_tensor_batch["ground_truth"]: 标准答案
        - data.non_tensor_batch["tag"]: 任务域标识
        
        返回:
        - rewards: torch.Tensor, shape (batch_size,)
        """
        responses = self.decode_responses(data)
        ground_truths = data.non_tensor_batch["ground_truth"]
        
        rewards = []
        for response, gt in zip(responses, ground_truths):
            if self.check_answer(response, gt):
                rewards.append(1.0)
            else:
                rewards.append(0.0)
        
        return torch.tensor(rewards)
```

然后在 YAML 中配置：
```yaml
rewards:
  my_task:
    worker_cls: roll.pipeline.rlvr.rewards.my_reward_worker.MyRewardWorker
    tag_included: [my_task_tag]
    world_size: 8
```

### Q3: 如何理解 `device_mapping` 的配置？

**A**: `device_mapping` 定义了一个角色使用哪些 GPU。它是一个 Python 表达式，会被 `eval()` 执行。

```yaml
# 使用 GPU 0-7
device_mapping: list(range(0,8))

# 使用 GPU 0-15（跨两个节点，每节点 8 卡）
device_mapping: list(range(0,16))

# 使用特定 GPU
device_mapping: "[0, 1, 4, 5]"

# 不使用 GPU（CPU only）
device_mapping: null
```

**关键规则**:
- `world_size = len(device_mapping) / num_gpus_per_worker`
- 对于 vLLM/SGLang，`num_gpus_per_worker` 自动根据 `tensor_parallel_size` 设置
- 对于 Megatron，每个 Worker 使用 1 个 GPU，TP/PP 通过 NCCL 通信实现
- 不同角色的 `device_mapping` 可以重叠（colocated）或不重叠（disaggregated）

**示例**: 16 GPU 的典型分配：
```yaml
actor_train:
  device_mapping: list(range(0,16))   # 16 个 Worker，每个 1 GPU
  strategy_args:
    strategy_name: megatron_train
    strategy_config:
      tensor_model_parallel_size: 2   # TP=2, 实际 dp_size=8

actor_infer:
  device_mapping: list(range(0,12))   # 6 个 Worker，每个 2 GPU
  strategy_args:
    strategy_name: vllm
    strategy_config:
      tensor_parallel_size: 2         # 自动设置 num_gpus_per_worker=2

reference:
  device_mapping: list(range(0,16))   # 与 actor_train 共享 GPU
```

### Q4: `rollout_batch_size`、`per_device_train_batch_size`、`gradient_accumulation_steps` 之间是什么关系？

**A**: 这三个参数共同决定了每步训练的数据量：

```
每步生成的样本数 = rollout_batch_size × num_return_sequences_in_group
                 = 64 × 8 = 512

每步训练的样本数 = per_device_train_batch_size × gradient_accumulation_steps × dp_size
                 = 1 × 32 × 16 = 512
```

**约束**: 两者必须相等（或训练样本数是生成样本数的整数倍，通过 `ppo_epochs` 控制）。

**调优建议**:
- `rollout_batch_size`: 越大越好（提高推理 GPU 利用率），但受显存限制
- `per_device_train_batch_size`: 通常设为 1-2（受训练显存限制）
- `gradient_accumulation_steps`: 用于凑齐总 batch size
- `num_return_sequences_in_group`: GRPO 通常设为 4-16，Reinforce++ 可以更小

### Q5: 如何选择 `adv_estimator`（优势估计方法）？

**A**:

| 方法 | 适用场景 | 优缺点 |
|------|---------|--------|
| `reinforce` | RLVR 默认 | 简单高效，使用 running mean 基线，不需要 Critic |
| `grpo` | RLVR 多 response | 组内标准化，需要 `num_return_sequences ≥ 2`，效果好 |
| `gae` | 需要精确 Value 估计 | 需要 Critic 网络，资源开销大，但理论上更优 |
| `rloo` | RLVR 多 response | Leave-one-out 基线，方差更低 |

**推荐**:
- 资源充足 + 多 response: 使用 `grpo`
- 资源有限: 使用 `reinforce`
- 需要 step-level 奖励: 使用 `gae`（需要 Critic）

### Q6: 训练过程中 KL 散度持续增大怎么办？

**A**: KL 散度增大说明策略模型偏离参考模型过多，可能导致模型退化。解决方案：

1. **启用 KL 惩罚**:
```yaml
add_token_level_kl: true
init_kl_coef: 0.01        # KL 惩罚系数
target_kl: 0.1             # 目标 KL 值
kl_horizon: 10000          # Adaptive KL 的调整窗口
```

2. **降低学习率**: 减小策略更新的步长
3. **增大 `ppo_epochs`**: 在同一批数据上多次更新，但每次更新幅度更小
4. **使用 Dual Clip**: `dual_clip_loss: true` 限制负 advantage 的更新幅度
5. **检查 Reference 模型**: 确保 Reference 模型正确加载且未被更新

### Q8: Megatron 和 DeepSpeed 应该怎么选？

**A**:

| 维度 | Megatron | DeepSpeed |
|------|----------|-----------|
| **适用规模** | 大模型（7B+） | 中小模型（≤7B） |
| **并行方式** | TP + PP + CP + EP | ZeRO（数据并行） |
| **显存效率** | 更高（TP 切分权重） | 较低（ZeRO-3 需要通信） |
| **配置复杂度** | 较高（需要设置 TP/PP） | 较低（只需设置 ZeRO stage） |
| **模型转换** | 需要 HF → Megatron 转换 | 直接使用 HF 模型 |
| **LoRA 支持** | 通过 mcore_adapter | 原生支持 |

**推荐**:
- **7B 以下**: DeepSpeed ZeRO-2/3
- **7B-72B**: Megatron（TP=2/4）
- **MoE 模型**: Megatron（TP + EP）
- **快速实验**: DeepSpeed（配置简单）
- **生产训练**: Megatron（性能更优）

### Q9: 如何理解 ROLL 中的 `ppo_epochs`？

**A**: `ppo_epochs` 控制在同一批 rollout 数据上执行多少轮策略梯度更新。

```
ppo_epochs=1: 每批数据只训练 1 轮（on-policy，数据最新鲜）
ppo_epochs=4: 每批数据训练 4 轮（数据复用，但可能 off-policy）
```

**权衡**:
- **ppo_epochs=1**: 数据利用率低，但策略更新最稳定（推荐用于 RLVR）
- **ppo_epochs=4**: 数据利用率高，但需要更严格的 clip 约束（推荐用于 PPO）

**注意**: 在 RLVR 场景下，由于 rollout 是最耗时的阶段，增大 `ppo_epochs` 可以在不增加 rollout 开销的情况下提高训练效率。但过大的 `ppo_epochs` 会导致策略偏离 rollout 时的分布，降低训练效果。

### Q10: `max_len_mask` 和 `difficulty_mask` 分别是什么？

**A**: 这两个是 ROLL 的**样本级别过滤机制**，用于提高训练数据质量：

**max_len_mask**:
- 过滤达到最大生成长度的样本
- 原因：达到最大长度的 response 通常是被截断的不完整回答，奖励信号不可靠
- 配置：`max_len_mask: true`

**difficulty_mask**:
- 过滤过于简单或过于困难的 prompt
- 过于简单（正确率 > 95%）：模型已经掌握，继续训练收益低
- 过于困难（正确率 < 10%）：模型无法学习，梯度信号噪声大
- 配置：
```yaml
difficulty_mask: true
difficulty_low_threshold: 0.1    # 正确率下限
difficulty_high_threshold: 0.95  # 正确率上限
```

**计算方式**: 对同一 prompt 的 K 个 response，计算正确率 = 正确数 / K。

### Q12: ROLL 的日志系统是怎样的？

**A**: ROLL 使用自定义的日志系统（`roll/utils/logging.py`）：

```python
from roll.utils.logging import get_logger
logger = get_logger()
```

**日志目录**: 由 `logging_dir` 配置，默认为 `./output/logs/{exp_name}/`

**日志级别**: 通过环境变量 `ROLL_LOG_LEVEL` 控制

**在 Ray Actor 中**: 每个 Worker 有独立的 logger，日志会包含 Worker 名称，便于区分：
```
[actor_train-0] INFO: training step 1 completed
```

**追踪器日志**: 通过 `track_with` 配置的追踪器（TensorBoard/WandB/SwanLab）记录训练指标，与文件日志独立。

### Q13: 如何理解 ROLL 中的 `generate_opt_level`？

**A**: `generate_opt_level` 控制 Rollout 阶段的优化级别：

**Level 0（基础模式）**:
- 将整个 batch 一次性发送给所有 DP Worker
- 同步等待所有 Worker 完成
- 简单可靠，但存在长尾延迟问题

**Level 1（异步模式）**:
- 逐条将请求分发到各 DP Worker
- 使用负载均衡策略选择最空闲的 Worker
- 每个 response 完成后立即回调
- 消除长尾延迟，提高 GPU 利用率

**选择建议**:
- 调试阶段使用 Level 0（简单可靠）
- 生产训练使用 Level 1（性能更优）
- 当 response 长度方差很大时，Level 1 的优势更明显

### Q14: 如何理解 `num_return_sequences` 和 `is_num_return_sequences_expand`？

**A**:

**num_return_sequences**: 每个 prompt 生成多少个 response。在 GRPO 中通常设为 4-16，用于组内对比。

**is_num_return_sequences_expand**: 控制多 response 的生成方式：

- `false`（默认）: 一次调用生成 N 个 response（vLLM/SGLang 原生支持）
- `true`: 将 prompt 复制 N 份，每份独立生成 1 个 response

**区别**:
- `false`: 效率更高（共享 KV Cache），但多样性可能较低
- `true`: 每个 response 完全独立采样，多样性更高，但效率较低

**推荐**: 默认使用 `false`，如果发现生成多样性不足再尝试 `true`。

### Q15: ROLL 中的 `tag` 机制是如何工作的？

**A**: `tag` 是 ROLL 多任务训练的核心机制：

1. **数据标记**: 每条训练数据在预处理时被标记一个 `tag`（如 `math_rule`、`code_sandbox`）
2. **采样控制**: `domain_interleave_probs` 按 tag 控制各任务的采样比例
3. **奖励路由**: Reward Worker 通过 `tag_included` 声明自己处理哪些 tag 的数据
4. **指标分组**: 训练指标按 tag 分组追踪（如 `reward/math_rule/mean`）

**数据流**:
```
数据集 → 按 tag 采样 → Rollout → 按 tag 路由到 Reward Worker → 合并奖励 → 训练
```

**tag 的来源**: 通常由数据集中的 `data_source` 字段决定，也可以在 `data_args` 中通过文件名映射。

### Q16: 如何监控训练进度和诊断问题？

**A**: ROLL 提供多种监控手段：

1. **TensorBoard/WandB**: 实时查看训练曲线
   ```bash
   tensorboard --logdir=./output/tensorboard/
   ```

2. **关键指标解读**:
   - `reward/*/mean` 持续上升 → 训练正常
   - `train/policy_loss` 持续下降 → 策略在改进
   - `train/kl` 持续增大 → 策略偏离过多，需要调整
   - `train/entropy` 持续下降 → 策略变得过于确定，可能过拟合
   - `train/clip_fraction` 过高（>0.3）→ 学习率可能过大

3. **Rollout 日志**: 设置 `rollout_dump_dir` 保存生成的 response，人工检查质量

4. **系统指标**:
   - `time/step_rollout`: Rollout 耗时（通常是瓶颈）
   - `time/step_train`: 训练耗时
   - `system/tokens_per_second`: 系统吞吐量

5. **Ray Dashboard**: `http://<head_node>:8265` 查看 Ray 集群状态

### Q18: 如何理解 ROLL 中的 `checkpoint_config`？

```yaml
checkpoint_config:
  type: file_system           # 保存类型
  output_dir: /data/ckpts     # 保存路径
```

### Q19: ROLL 中的 `reward_system_config` 是什么？

**A**: `reward_system_config` 是 ROLL 的奖励系统配置，支持更灵活的奖励计算方式：

```yaml
reward_system_config:
  type: rule_based           # 基于规则的奖励
  # 或
  type: model_based          # 基于模型的奖励
  model_name_or_path: path/to/reward_model
```

在 RLVR Pipeline 中，奖励系统通过 `rewards` 字段配置多个 Reward Worker，每个 Worker 负责一种类型的奖励计算。这种设计允许同一个训练任务混合使用规则奖励（数学答案匹配）和模型奖励（LLM Judge）。

### Q22: 数据并行（DP）、张量并行（TP，层内部切分并行）、流水线并行（PP，层间串行执行）分别是什么，在RL中的作用？

**A**:
在深度学习和现代强化学习（尤其是基于大语言模型的 RLHF，即基于人类反馈的强化学习）中，随着模型参数量的爆炸式增长，单张 GPU 的显存和算力早已无法满足需求。因此引入了分布式训练技术。

**数据并行（DP）、张量并行（TP）和流水线并行（PP）**被称为“3D 并行”的核心技术。下面我将分别解释它们的原理，并重点说明它们在强化学习（RL）中的具体作用。

---

#### 1. 数据并行（Data Parallelism, DP）

**什么是 DP？**
*   **原理**：将**完整的模型**复制到每一张 GPU 上。在训练时，将全局的 Batch 数据（比如 1024 条数据）切分成多个小的 Mini-batch（比如 8 张卡，每张卡分 128 条）。
*   **过程**：各 GPU 独立前向传播和反向传播计算梯度，然后通过通信（All-Reduce 操作）对所有 GPU 上的梯度进行求和平均，最后更新各自的模型权重，确保所有 GPU 上的模型始终一致。
*   **进阶**：由于传统 DP 每张卡都要存完整模型及优化器状态，显存压力极大。现在常用的是其进阶版 **ZeRO（零冗余优化器）**，它在保持 DP 逻辑的同时，把模型参数、梯度和优化器状态分摊到了多张卡上。

**在 RL 中的作用：**
*   **加速经验收集（Rollout）**：强化学习需要智能体（Agent）不断与环境交互产生数据。DP 允许我们在多个 GPU 上同时运行多个环境和策略模型，**极大地加快了采样速度**（即分布式 Actor 架构）。
*   **提升吞吐量**：在 PPO 等算法的更新阶段，可以处理更大的 Batch Size，使梯度下降的方向更稳定。
*   **局限性**：在 RLHF 中，通常需要同时加载 4 个模型（Actor, Critic, Reward, Reference）。如果单卡显存装不下哪怕一个模型，纯 DP 就彻底失效了，必须依赖 ZeRO 或结合 TP/PP。

---

#### 2. 张量并行（Tensor Parallelism, TP）

**什么是 TP？**
*   **原理**：也叫**层内切分**。它不切分数据，也不按层切分模型，而是把**某一层内部的巨大矩阵运算（如全连接层、注意力机制中的矩阵乘法）切开**，分配到不同的 GPU 上。
*   **过程**：比如一个大矩阵 $A$ 乘以 $B$，把 $B$ 按列切分成 $B_1$ 和 $B_2$ 放到两张卡上，两张卡分别计算一部分结果，然后通过通信（All-Gather 等）把结果拼接起来，再传给下一层。
*   **特点**：极度依赖极高的显存间通信带宽（如 NVLink）。通常局限在单一节点（一台 8 卡服务器）内部使用。

**在 RL 中的作用：**
*   **打破单卡显存瓶颈**：让几百亿参数的 Actor 和 Critic 模型能够加载到显存中。
*   **极速的生成体验（Inference/Rollout）**：在 RLHF 中，PPO 算法有很大一部分时间花在 Actor 模型**自回归生成文本（Rollout）**上。TP 因为是将每一层的计算分摊到多张卡，显存带宽聚合了，计算延迟极低。**TP 是加速强化学习文本生成阶段的最有效手段。**
*   **减少显存碎片**：大张量被切小，有效缓解了 RL 训练中极易出现的 OOM（内存溢出）问题。

---

#### 3. 流水线并行（Pipeline Parallelism, PP）

**什么是 PP？**
*   **原理**：也叫**层间串行切分**。像工厂流水线一样，把一个模型**按层级砍成几段**。比如一个 80 层的模型，GPU 0 负责 1-20 层，GPU 1 负责 21-40 层，依次类推。
*   **过程**：GPU 0 计算完前 20 层后，把中间激活值（Hidden States）传给 GPU 1；以此类推。反向传播时，梯度从最后的 GPU 依次往前传。
*   **特点**：存在“流水线气泡（Bubble）”问题，即 GPU 0 在等待后方的 GPU 计算时处于闲置状态。为了缓解这个问题，通常会将一个 Batch 切分成更小的 Micro-batch 送入流水线。由于只需传输层间激活值，对网络通信带宽要求较低，**适合跨节点（多台机器之间）并行**。

**在 RL 中的作用：**
*   **支持超大规模 RLHF 训练**：当模型大到 8 张卡的 TP 也装不下时（例如 100B 以上的模型），必须使用 PP 跨越多个节点。
*   **多模型分离部署（RL 专属优化）**：RLHF 相比普通训练更复杂，因为它有 4 个模型。使用 PP 思路，我们可以进行**模型级别的流水线并行**：
    *   把 Actor 模型和 Reference 模型部署在节点 A 的机器上。
    *   把 Critic 模型和 Reward 模型部署在节点 B 的机器上。
    *   在 Rollout 阶段，节点 A 生成文本，传给节点 B 计算 Reward 和 Value，大大降低了单台机器的显存压力。

---

#### 总结与对比（以大模型 RLHF 为例）

| 并行方式 | 切分对象 | 显存利用 | 通信开销 | 在 RL 中的核心价值（PPO/RLHF） |
| :--- | :--- | :--- | :--- | :--- |
| **DP (数据)** | Batch 数据 | 单卡仍需容纳完整模型（除非用 ZeRO） | 中等（传递梯度） | 并发收集环境经验，增大训练吞吐量，提升梯度稳定性。 |
| **TP (张量)** | 矩阵运算（层内） | 显著降低单卡显存 | 极高（每次运算都在通信） | **加速 Actor 模型的自回归文本生成**，让超大模型单次前向传播极速完成。 |
| **PP (流水线)** | 网络层数（层间） | 显著降低单卡显存 | 较低（仅传递中间激活值） | 跨服务器部署超大模型；或在不同机器间**隔离部署 Actor 和 Critic**，解决 4 模型同驻显存的 OOM 问题。 |

**在目前顶级的 RLHF 训练框架（如 DeepSpeed-Chat, Megatron-LM, vLLM 等）中，通常是 3D 并行火力全开的：**
机器内部使用 **TP** 保证推理生成速度，机器之间使用 **PP** 容纳下几百亿参数的 4 个模型，并在整体外部套上 **DP (ZeRO)** 来处理海量的 Prompt 数据并加速模型参数更新。
