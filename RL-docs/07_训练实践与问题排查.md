## ROLL 训练实践与问题排查

> 本文档基于高德地图 Agentic RL 项目的**真实训练经验**，记录从环境搭建、SFT 冷启动、RL 训练到问题排查的完整实践过程。涵盖 11 轮 SFT 迭代、11+ 轮 RL 版本迭代中积累的参数选择、Reward 设计、数据筛选策略和踩坑记录。

---

### 一、环境准备

#### 1.1 Docker 环境

统一使用官方 Docker 镜像，避免环境差异导致的问题：

```bash
sudo docker run -dit \
     --cap-add SYS_ADMIN --gpus all \
     --name=${USER}_roll_dev \
     --ipc=host --net=host \
     -v /dev/fuse:/dev/fuse -v /dev/shm:/dev/shm \
     -v /home/$USER/:/home/$USER/ \
     -v /var/run/docker.sock:/var/run/docker.sock \
     -v /mnt/ram:/mnt/ram \
     roll-registry.cn-hangzhou.cr.aliyuncs.com/roll/pytorch:nvcr-24.05-py3-torch260-vllm084 \
     /bin/bash
```

**关键注意事项**：
- 必须 `--ipc=host --net=host`，否则 NCCL 通信和 Ray 集群会出问题
- 必须挂载 `/dev/shm`，RL 训练的共享内存需求很大（后续会重新挂载到 81920M）
- 镜像版本要和 `requirements_torch260_vllm.txt` 匹配，不要混用 torch 版本

#### 1.2 依赖安装

```bash
pip install -r requirements_common.txt \
    --trusted-host mirrors.aliyun.com \
    --index-url https://mirrors.aliyun.com/pypi/simple/

# 根据推理后端选择安装（二选一）
pip install -r requirements_torch260_vllm.txt    # vLLM 后端
pip install -r requirements_torch260_sglang.txt   # SGLang 后端
```

**核心依赖版本约束**（踩坑总结）：

| 依赖 | 版本要求 | 说明 |
|------|---------|------|
| `ray[default,cgraph]` | ≥2.48.0 | vLLM 要求，低版本会报 cgraph 错误 |
| `datasets` | ==3.1.0 | 高版本 API 不兼容 |
| `peft` | ==0.12.0 | LoRA 相关，版本敏感 |
| `accelerate` | ==0.34.2 | 与 DeepSpeed 配合使用 |
| `trl` | ==0.9.6 | LLM Judge Reward Worker 依赖 |
| `numpy` | <2.0 | numpy 2.0 有大量 breaking changes |

#### 1.3 多节点环境初始化

```bash
source "examples/scripts/env_setup.sh"
pre_setup_environment
```

脚本自动处理：
1. **设置 NCCL 网络接口**：多节点用 `eth0`，单节点用 `bond0`
2. **扩大 `/dev/shm`**：重新挂载到 81920M，默认大小不够用
3. **主节点发现**：RANK=0 的节点写入调度文件，其他节点轮询等待

**常见问题**：多节点启动后卡住不动，大概率是 RANK≠0 的节点找不到调度文件，检查 OSS 挂载路径 `/data/oss_bucket_0/mdl_schduler_mock/` 是否可写。

### 二、RLVR 训练实践

#### 2.1 启动方式

```bash
# 本地直接启动（开发调试用）
bash examples/qwen2.5-7B-rlvr_megatron/run_rlvr_pipeline.sh

# 通过 Nebula 集群提交（生产训练用）
bash examples/qwen2.5-7B-rlvr_megatron/submit_pipeline.sh
```

#### 2.2 核心训练参数（Qwen2.5-7B RLVR）

##### 全局参数

| 参数 | 实际值 | 选择理由 |
|------|--------|---------|
| `max_steps` | 500 | 7B 模型通常 300-500 步收敛，再多容易过拟合 |
| `rollout_batch_size` | 64 | 乘以 `num_return_sequences_in_group=8` 得到 512 个 response |
| `prompt_length` | 2048 | 覆盖大部分数学/代码题目 |
| `response_length` | 4096 | 数学推理需要较长的 CoT |

##### RL 策略参数

| 参数 | 实际值 | 选择理由 |
|------|--------|---------|
| `num_return_sequences_in_group` | 8 | 每个 prompt 生成 8 个 response，用于组内对比 |
| `adv_estimator` | reinforce | Reinforce++ 算法，不需要 Critic 网络，省资源 |
| `dual_clip_loss` | true | 限制负 advantage 的更新幅度 |
| `whiten_advantages` | true | Advantage 白化（标准化），稳定梯度 |
| `difficulty_mask` | true | 过滤过简单（>95%）或过难（<10%）的 prompt |

##### Actor Train 参数

| 参数 | 实际值 | 选择理由 |
|------|--------|---------|
| `learning_rate` | 1.0e-6 | RL 学习率比 SFT 低 1-2 个数量级，防止策略崩溃 |
| `per_device_train_batch_size` | 1 | 受显存限制，7B 模型每卡只能放 1 个样本 |
| `gradient_accumulation_steps` | 32 | 16 卡 × 1 × 32 = 512，与 rollout 生成量对齐 |

**batch size 对齐公式**：
```
rollout 生成量 = rollout_batch_size × num_return_sequences_in_group = 64 × 8 = 512
训练消耗量   = per_device_train_batch_size × gradient_accumulation_steps × dp_size
             = 1 × 32 × 16 = 512  ✅ 对齐
```

> ⚠️ **这两个值必须相等**，否则训练会报错或数据对不上。

#### 2.3 多任务混合训练

RLVR 训练同时覆盖 5 个任务域，每个域对应不同的 Reward Worker：

| 任务域 | 采样比例 | Reward Worker | 是否需要 GPU |
|--------|---------|--------------|-------------|
| `math_rule` | 40% | MathRuleRewardWorker | ❌ |
| `code_sandbox` | 30% | CodeSandboxRewardWorker | ❌ |
| `llm_judge` | 10% | LLMJudgeRewardWorker | ✅ |
| `ifeval` | 10% | GeneralRuleRewardWorker | ❌ |
| `crossthinkqa` | 10% | CrossThinkQARuleRewardWorker | ❌ |

> ⚠️ **LLM Judge 的 GPU 不能和 Actor Infer 共享**。

#### 2.4 验证集配置

训练 vs 验证的生成参数差异：训练时用高温度（0.99）鼓励探索，验证时用低温度（0.6）追求最佳表现。

```yaml
validation:
  generating_args:
    top_p: 0.6
    temperature: 0.6
    num_return_sequences: 1
```

### 三、Agentic RL 训练实践

#### 3.1 启动方式

```bash
ray stop --force           # 先清理旧的 Ray 进程
fuser -k 6379/tcp          # 释放 Redis 端口
python examples/start_agentic_pipeline.py \
    --config_path qwen3-4b-2507-agentic \
    --config_name agentic_amap
```

> ⚠️ Agentic 训练前**必须先 `ray stop --force`**，否则残留的 Ray 进程会导致资源冲突。

#### 3.2 核心训练参数（Qwen3-4B Agentic）

##### 与 RLVR 的关键差异

| 参数 | RLVR (7B) | Agentic (4B) | 差异原因 |
|------|-----------|-------------|---------|
| `sequence_length` | 6144 | 40960 | 多轮交互轨迹很长 |
| `rollout_batch_size` | 64 | 512 | Agentic 需要更多环境并行 |
| `adv_estimator` | reinforce | grpo | GRPO 在 Agentic 场景效果更好 |
| `max_grad_norm` | 未设置 | 1.0 | 多轮交互梯度波动大，需要裁剪 |
| `use_kl_loss` | false | true (0.001) | 防止策略偏离过大 |
| `async_generation_ratio` | 未使用 | 4 | 异步生成，提高吞吐 |

##### Agentic 特有参数

| 参数 | 实际值 | 说明 |
|------|--------|------|
| `max_tokens_per_step` | 4096 | 每轮交互 Agent 最多生成 4096 token |
| `max_actions_per_traj` | 15 | 每条轨迹最多 15 轮交互 |
| `async_generation_ratio` | 4 | 异步生成比例，4 表示同时跑 4 倍的环境 |
| `enable_thinking` | true | 启用 thinking 模式（Qwen3 特有） |

##### 环境管理器配置

```yaml
train_env_manager:
  max_env_num_per_worker: 4    # 每个 Worker 最多管理 4 个环境
  num_env_groups: 64           # 64 个环境组
  group_size: 8                # 每组 8 个环境（同组共享 prompt 和 seed）
  tags: [AmapReward]           # 环境类型标签

val_env_manager:
  group_size: 1                # 验证时 group_size=1，温度为 0 时相同输入必然相同输出
```

> **`group_size` 的含义**：同一组内的环境使用相同的 prompt 和 seed，生成不同的 response 用于 GRPO 组内对比。

##### Agentic 场景下的 Batch Size 语义变化

在 Agentic 的 setting 下，所有跟 batch size 相关的参数是指**轨迹数量**而不是 query 数量。计算公式：

```
dp = gpus / (tp * cp * pp)    # ep 不算在内
ga = rollout_batch_size / dp
```

##### GPU 资源分配（大规模 Agentic 训练）

```yaml
infer_device: list(range(0,16))      # 16 卡推理
train_device: list(range(16,144))    # 128 卡训练
```

Agentic 训练需要更多训练卡，因为 `sequence_length=40960` 极长，使用 `context_parallel_size: 8` 将长序列切分到 8 张卡。

##### 动态 Batching 配置

```yaml
actor_train:
  use_dynamic_batching_in_train: true
  max_tokens_per_microbatch_in_train: 40960
  sequence_length_round_in_train: 128
```

Agentic 训练的轨迹长度差异极大（有的 2 轮就结束，有的 15 轮），动态 batching 按 token 数而非样本数组 batch，避免 padding 浪费。

#### 3.3 训练时间基准

##### 4B-Instruct-2507 配置

30000 数据，128 卡，40K 长度，`tp=pp=ep=1, cp=4, ga=16`：

| rollout_batch_size | num_env_groups | 每步耗时 | 每 epoch 耗时 |
|-------------------|---------------|---------|-------------|
| 512 | 64 | ~2 min | ~20 hours |

##### 30B-A3B 配置

30000 数据，128 卡，40K 长度，`tp=2, pp=4, ep=2, cp=4, ga=128`：

| rollout_batch_size | num_env_groups | 每步耗时 | 每 epoch 耗时 |
|-------------------|---------------|---------|-------------|
| 256 | 32 | ~3 min | ~30 hours |

#### 3.4 SFT 冷启动的必要性

Agentic 训练通常不直接从 base 模型开始，而是先做 SFT：

```yaml
pretrain: /path/to/sft_checkpoint
```

**为什么不直接从 base 模型开始？** Agent 需要先学会基本的工具调用格式（如 function calling），否则 RL 训练初期几乎所有 response 都是无效的，奖励全为 0，无法学习。

### 四、训练数据筛选策略

#### 4.1 数据质量评分体系

训练数据按难度分为 7 个等级：

| 分数 | 含义 | 处理方式 |
|------|------|---------|
| -1 | 不可执行（缺少关键信息或超出工具范围） | 过滤掉 |
| 0 | 无需工具（闲聊/通用知识） | 过滤掉 |
| 1 | 非常简单（原子操作） | 保留但降权 |
| 2 | 简单（线性链式调用） | 保留 |
| 3 | 中等（条件/参数化） | **核心训练数据** |
| 4 | 困难（多意图/优化） | **核心训练数据** |
| 5 | 非常困难（复杂推理/边界情况） | **核心训练数据** |

实际训练中，筛选难度为 [3, 4, 5, 6, 7] 的数据，目标约 3 万条。

#### 4.2 平滑采样策略

为了**提高长尾数据的采样比例**，使用平滑系数控制采样权重：

设某文件的原始有效数据量为 N，平滑系数为 α（Smoothing Factor），则：

- **权重**：W = N^α
- **采样数量**：Target = TotalSample × W / ΣW_all
- **保护策略**：有效数据条数少于 300 的文件全部保留

实际使用 `SMOOTHING_FACTOR = 0.6` 配合多样性 TopK 筛选。

#### 4.3 数据质量问题

需要注意的数据质量陷阱：
- **缺少上下文的多轮对话片段**：部分 query 是从多轮对话中间抽取的，缺少上下文信息（如"之后到那个博物馆那里之后叫个外卖"）
- **不可执行的 query**：关键实体缺失（如"去那个商场"但没有上下文）
- **超出工具范围的 query**：意图明确但功能不在 Agent 能力范围内

### 五、Reward 设计实践

#### 5.1 LLM Judge Reward 函数

Agentic 场景使用 LLM 作为评判者（LLM Judge）来计算 Reward：

```python
def compute_reward(self, response):
    if response is None:
        return 0.0 if random.randint(0, 5) < 2 else 1.0
    scores = self.extract_all_final_scores(response)
    if len(scores) == 0:
        return 0.5  # 格式异常时不奖励也不惩罚
    reward_score = float(scores[-1])
    return reward_score
```

**关键设计决策**：
- **LLM Judge 无输出或格式异常时，reward 统一设为 0.5**：既不奖励也不惩罚，避免因评判模型自身问题影响训练
- **Tool reward 设为 0**：早期版本中负 tool reward 设置过于极端，限制了模型的工具调用能力，后续迭代中将 tool reward 设为 0

#### 5.2 Reward 设计的踩坑经验

| 版本 | Reward 策略 | 问题 | 解决方案 |
|------|-----------|------|---------|
| RL v1 | 默认 reward | 基线版本 | - |
| RL v2 | reward Prompt v1 | 评判标准不够精确 | 迭代 Prompt |
| RL v4 | 负 tool reward 过于极端 | 限制了模型的工具调用 | 将 tool reward 设为 0 |
| RL v7 | tool reward 设为 0 + 更换 SFT 筛选数据 | 效果改善 | 继续沿用 |

#### 5.3 BT Reward vs LLM Judge Reward 对比

实际测试中，Qwen Plus Latest 作为 LLM Judge 的评分与 BT Reward Model 的评分相关性较低：

```
Pearson Correlation:  0.2847
Spearman Correlation: 0.1590
```

这说明两种 Reward 信号捕捉的是不同维度的质量信号，可以考虑组合使用。

### 六、关键训练参数调优指南

#### 6.1 学习率

| 场景 | 推荐学习率 | 说明 |
|------|-----------|------|
| RLVR 7B | 1.0e-6 | 标准选择 |
| RLVR 72B | 5.0e-7 | 大模型用更小的学习率 |
| Agentic 4B | 1.0e-6 | 与 RLVR 类似 |
| SFT 预训练 | 1.0e-5 ~ 5.0e-6 | SFT 学习率比 RL 高一个数量级 |

**经验法则**：如果训练过程中 reward 突然暴跌或 KL 散度飙升，第一件事就是降低学习率。

#### 6.2 num_return_sequences_in_group vs group_size

**重要区分**：在 RLVR 和 Agentic 场景下，组大小的控制参数不同：

- **RLVR**：由 `num_return_sequences_in_group` 控制，针对每条 prompt 的采样数（vLLM 的 n 参数）
- **Agentic**：由 `group_size` 控制，同组环境共享 prompt 和 seed

| 值 | 适用场景 | 权衡 |
|----|---------|------|
| 4 | 资源有限 | 组内对比信息少，但推理开销小 |
| 8 | **推荐默认值** | 平衡效果和开销 |
| 16 | 追求最佳效果 | 推理开销翻倍，但 GRPO 效果更好 |

#### 6.3 temperature 和 top_p

| 阶段 | temperature | top_p | 说明 |
|------|------------|-------|------|
| 训练 Rollout | 0.99 | 0.99 | 高温度 + 高 top_p = 最大探索 |
| 验证 | 0.6 | 0.6 | 低温度 = 追求最佳表现 |
| LLM Judge | 0.8 | 0.8 | 中等温度，评判需要一定确定性 |

#### 6.4 difficulty_mask 阈值

```yaml
difficulty_low_threshold: 0.1    # 正确率 < 10% 的 prompt 太难，过滤
difficulty_high_threshold: 0.95  # 正确率 > 95% 的 prompt 太简单，过滤
```

**调优建议**：
- 训练初期模型较弱，可以放宽下限到 0.05
- 训练后期模型变强，可以收紧上限到 0.9
- 如果发现 reward 不涨，检查是否大量数据被过滤掉了

#### 6.5 Rollout Batch 设置经验

```
rollout_batch_size 一般设置为 512
dp = gpus / (tp * cp * pp)    # ep 不算在内
ga = rollout_batch_size / dp
```

由于使用异步 rollout（`async_generation_ratio=4`），实际会有 off-policy 的数据。`num_env_groups` 设置和 `val_batch_size` 一样。

### 七、SFT 迭代记录

#### 7.1 SFT 版本演进

共经历 11 轮 SFT 迭代，关键版本节点：

| SFT 版本 | 基础模型 | 关键变更 | 用于 RL 版本 |
|---------|---------|---------|------------|
| SFT 7 | Qwen3-30B-A3B-Think | 早期版本 | RL v5 |
| SFT 10 | Qwen3-4B-Thinking-2507 | 更换筛选数据 | RL v8 |
| SFT 11 | Qwen3-30B-A3B-Inst | 最终稳定版本 | RL v6, v7 |

#### 7.2 RL 版本迭代记录

| RL 版本 | 基础 SFT | 模型 | 算法 | 关键变更 | 结果 |
|--------|---------|------|------|---------|------|
| v1 | - | 4B | GSPO | 基线版本 | 基线 |
| v2 | - | 4B | GSPO | reward Prompt v1 | - |
| v3 | v2 基础 | 30B-A3B | GSPO | tp=pp=ep=cp=2 | OOM |
| v4 | v2 基础 | 30B-A3B | GSPO | tp=cp=2,pp=ep=4 | 负 tool reward 过于极端 |
| v5 | SFT7 | 30B-A3B-Think | GSPO | - | 工具连接 timeout |
| v6 | SFT11 | 30B-A3B-Inst | GSPO | - | 正常训练 |
| v7 | SFT11 | 30B-A3B-Think-2507 | GSPO | tool reward=0 | 效果改善 |
| v8 | SFT10 | 4B-Think-2507 | GSPO | tool reward=0 | 效果改善 |
| v9 | - | 30B-A3B-Think-2507 | GSPO | 32+256 卡 → 64+224 卡 | infer 资源不够导致挤占 |
| v10 | v9-ckpt120 | 30B-A3B-Think-2507 | GSPO | +40step BT, 64+192 卡 | 继续训练 |
| v11 | v9-ckpt120 | 30B-A3B-Think-2507 | GSPO | +40step hard 数据 | 继续训练 |

**关键经验**：
- **30B-A3B 模型的并行策略**：tp=pp=ep=cp=2 会 OOM，需要调整为 tp=cp=2, pp=ep=4
- **Infer 资源分配**：32 卡 infer + 256 卡 train 时，generate 会发生挤占导致瞬时 QPS 过高，调整为 64+224 后解决
- **断点续训**：v10 和 v11 都是从 v9 的 checkpoint-120 继续训练，分别尝试 BT reward 和 hard 数据

### 六、关键训练参数调优指南

#### 6.1 学习率

| 场景 | 推荐学习率 | 说明 |
|------|-----------|------|
| RLVR 7B | 1.0e-6 | 标准选择 |
| RLVR 72B | 5.0e-7 | 大模型用更小的学习率 |
| Agentic 4B | 1.0e-6 | 与 RLVR 类似 |
| SFT 预训练 | 1.0e-5 ~ 5.0e-6 | SFT 学习率比 RL 高一个数量级 |

**经验法则**：如果训练过程中 reward 突然暴跌或 KL 散度飙升，第一件事就是降低学习率。

#### 6.2 num_return_sequences_in_group vs group_size

**重要区分**：在 RLVR 和 Agentic 场景下，组大小的控制参数不同：

- **RLVR**：由 `num_return_sequences_in_group` 控制，针对每条 prompt 的采样数（vLLM 的 n 参数）
- **Agentic**：由 `group_size` 控制，同组环境共享 prompt 和 seed

| 值 | 适用场景 | 权衡 |
|----|---------|------|
| 4 | 资源有限 | 组内对比信息少，但推理开销小 |
| 8 | **推荐默认值** | 平衡效果和开销 |
| 16 | 追求最佳效果 | 推理开销翻倍，但 GRPO 效果更好 |

#### 6.3 temperature 和 top_p

| 阶段 | temperature | top_p | 说明 |
|------|------------|-------|------|
| 训练 Rollout | 0.99 | 0.99 | 高温度 + 高 top_p = 最大探索 |
| 验证 | 0.6 | 0.6 | 低温度 = 追求最佳表现 |
| LLM Judge | 0.8 | 0.8 | 中等温度，评判需要一定确定性 |

#### 6.4 difficulty_mask 阈值

```yaml
difficulty_low_threshold: 0.1    # 正确率 < 10% 的 prompt 太难，过滤
difficulty_high_threshold: 0.95  # 正确率 > 95% 的 prompt 太简单，过滤
```

**调优建议**：
- 训练初期模型较弱，可以放宽下限到 0.05
- 训练后期模型变强，可以收紧上限到 0.9
- 如果发现 reward 不涨，检查是否大量数据被过滤掉了

#### 6.5 Rollout Batch 设置经验

```
rollout_batch_size 一般设置为 512
dp = gpus / (tp * cp * pp)    # ep 不算在内
ga = rollout_batch_size / dp
```

由于使用异步 rollout（`async_generation_ratio=4`），实际会有 off-policy 的数据。`num_env_groups` 设置和 `val_batch_size` 一样。

#### 8.2 算法效果指标

##### 验证阶段

| 指标 | 含义 |
|------|------|
| `val/score/mean` | 验证阶段每个 episode 的平均分数，反映模型在未见过环境上的表现 |
| `val/score/max` / `val/score/min` | 验证阶段最高/最低分数 |

##### 奖励相关

| 指标 | 含义 | 正常范围 |
|------|------|---------|
| `critic/score/mean` | 环境原始奖励均值 | 持续上升 |
| `critic/rewards/mean` | 经过归一化/裁剪的奖励均值 | 持续上升 |
| `critic/advantages/mean` | 优势函数均值 | 接近 0 |
| `critic/returns/mean` | 回报均值 | 持续上升 |
| `tokens/response_length/mean` | 生成响应的平均长度 | 稳定或缓慢变化 |

##### 策略相关

| 指标 | 含义 | 异常信号 |
|------|------|---------|
| `actor/lr` | 策略网络学习率 | - |
| `actor/total_loss` | 策略梯度+KL+熵的加权总损失 | 震荡不收敛 → 学习率过大 |
| `actor/approxkl` | 当前策略与旧策略的近似 KL 散度 | >1.0 → 策略偏离过大 |
| `actor/kl_loss` | 当前策略与参考策略的 KL 散度惩罚 | 持续飙升 → 需要降低学习率 |
| `actor/clipfrac` | 策略裁剪比例 | 过高说明更新步长过大 |
| `critic/entropy/mean` | 策略的平均熵 | 骤降到 0 → 模式坍缩 |

##### 价值相关（使用 Critic 时）

| 指标 | 含义 |
|------|------|
| `critic/loss` | 价值网络预测值与真实回报之间的损失 |
| `critic/value` | 旧策略的价值网络预测值均值 |
| `critic/vpred` | 当前优化中的价值网络预测值均值 |
| `critic/error` | 价值网络预测值与真实回报的均方误差 |

#### 8.3 框架性能指标

##### 全局系统指标

| 指标 | 含义 |
|------|------|
| `system/tps` | 每秒处理的 tokens 数量，衡量系统吞吐量 |
| `system/samples` | 已处理的总样本数 |

##### 阶段耗时指标

| 指标 | 含义 |
|------|------|
| `time/rollout` | 数据收集阶段耗时 |
| `time/{stage}/total` | 某阶段总执行时间（含 offload/onload） |
| `time/{stage}/execute` | 某阶段实际业务逻辑执行时间 |
| `time/{stage}/onload` | 模型状态加载到 GPU 的时间 |
| `time/{stage}/offload` | 模型状态从 GPU 卸载的时间 |

其中 `{stage}` 包括：`train_step`、`generate`、`model_update`、`compute_log_probs`、`do_checkpoint`、`compute_values`、`compute_rewards`。

##### GPU 内存指标

每个阶段在四个时间点记录内存快照：
1. **start/offload**：操作开始时（模型状态卸载后）
2. **start/onload**：模型状态加载后（业务逻辑执行前）
3. **end/onload**：业务逻辑执行后（模型状态卸载前）
4. **end/offload**：操作结束时（模型状态卸载后）

每个快照包含 `allocated`、`reserved`、`max_allocated`、`max_reserved` 四个维度。

### 九、常见问题与排查

#### 9.1 训练启动类问题

##### 问题：Ray 启动失败，端口被占用

```
Error: Redis connection error
```

**解决**：
```bash
ray stop --force
fuser -k 6379/tcp
```

##### 问题：NCCL 通信超时

```
RuntimeError: NCCL communicator was aborted
```

**排查步骤**：
1. 检查 `NCCL_SOCKET_IFNAME` 是否正确（多节点用 `eth0`，单节点用 `bond0`）
2. 检查防火墙是否放行了 NCCL 端口
3. 增大 `rpc_timeout`（默认 3600 秒）
4. 检查 `/dev/shm` 大小是否足够（需要 80G+）

##### 问题：vLLM 启动时 OOM

**解决**：
- 降低 `gpu_memory_utilization`（从 0.8 降到 0.7）
- 降低 `max_model_len`（确保 >= prompt_length + response_length 即可）
- 检查是否有其他进程占用 GPU 显存

##### 问题：Hydra 配置解析错误

**排查**：
- 检查 YAML 中的 `${}` 引用是否都有对应的定义
- 检查 `defaults` 引用的配置文件是否存在
- 使用 `OmegaConf.to_yaml(cfg, resolve=True)` 打印解析后的完整配置

#### 9.2 训练过程类问题

##### 问题：Reward 始终为 0

**可能原因**：
1. **数据格式错误**：`ground_truth` 字段缺失或格式不对
2. **tag 不匹配**：数据的 `tag` 和 Reward Worker 的 `tag_included` 对不上
3. **模型太弱**：base 模型完全不会做这类任务，需要先 SFT
4. **Reward Worker 报错但被静默吞掉**：检查 Reward Worker 的日志

**排查方法**：
```bash
python read_rollout_trajectory.py  # 项目根目录有这个脚本
```

##### 问题：Reward 上升后突然暴跌

**可能原因**：
1. **学习率过大**：策略更新步长太大，跳出了好的区域
2. **KL 散度过大**：策略偏离参考模型太远
3. **数据分布突变**：某个 domain 的数据突然变化

**解决方案**：
- 降低学习率到 5e-7
- 启用 `add_token_level_kl: true`，设置 `init_kl_coef: 0.01`
- 启用 `dual_clip_loss: true`
- 从暴跌前的 checkpoint 恢复，用更保守的参数继续训练

##### 问题：训练 loss 为 NaN

**可能原因**：
1. **梯度爆炸**：设置 `max_grad_norm: 1.0` 进行梯度裁剪
2. **数据异常**：某些样本的 log_prob 计算出现 inf
3. **精度问题**：FP16 溢出，改用 BF16

##### 问题：模型生成的 response 越来越短

**原因**：模型学会了"偷懒"——生成很短的回答也能获得部分奖励。

**解决方案**：
- 检查 `max_len_mask` 是否开启
- 在 Reward 中加入长度惩罚：`response_length_penalty_coef`
- 检查 Reward 设计是否有漏洞

##### 问题：训练速度越来越慢

**可能原因**：
1. **response 越来越长**：模型学会了生成更长的 CoT
2. **显存碎片化**：vLLM 的 KV Cache 碎片化，重启 Actor Infer 可以缓解
3. **数据加载瓶颈**：`preprocessing_num_workers` 设置过小

#### 9.3 Agentic 场景特有问题

##### 问题：工具调用时模型填入自身坐标而非地名

**现象**：模型在调用 `map_search_places` 等工具时，总是将自己当前的坐标填进去搜索，而不是直接用地名。

**原因**：可能混杂了来自 SFT 的知识，工具输入输出格式正常，reward 也很难判断这个轨迹不行。

**解决方案**：在 SFT 数据中增加正确使用地名搜索的示例，强化正确的工具调用模式。

##### 问题：工具调用不稳定（并发限制）

**现象**：粗略估计 41 条轨迹中出现 24 次工具调用失败，一条轨迹可能出现多次。

**影响**：工具调用出错导致轨迹得分很低，但这并不是模型本身的问题，只是运气不好碰到工具并发调用限制，会严重影响学习。

**解决方案**：
- 控制 `max_env_step_concurrent` 限制并发数
- 在 Reward 计算中对工具调用失败的情况做特殊处理

##### 问题：max_actions_per_traj 截断导致 Reward 下降

**现象**：当平均工具调用次数接近上限（如设置为 5）时，模型在达到上限后继续生成工具调用信息而不是总结，导致轨迹以工具调用结尾而非总结结尾，reward 明显下降。

**解决方案**：`max_actions_per_traj` 参数必须比 `max_tool_uses` 大，给模型留出生成总结的空间。实际训练中设置 `max_actions_per_traj=15`。

> 💡 **有趣的发现**：在继续训练的过程中，模型会自行修正这种错误，reward 继续上升。

##### 问题：从 SFT 冷启动训练出现乱码

**可能原因**：
1. SFT 模型的 thinking 部分是英语，与中文训练数据不匹配
2. 模型格式不兼容

##### 问题：30B-A3B 训练中断

**排查要点**：
1. 从 SFT 开始训练时开启了 KL，需要计算 reference，确保 reference 计算也配置了 dynamic batch
2. 大模型的 reference 计算显存需求大，需要合理分配资源

##### 问题：Rollout 出现相同的轨迹

**可能原因**：随机种子设置问题或 temperature 过低，导致同组环境生成完全相同的轨迹。

**解决方案**：确保训练时 temperature 足够高（推荐 0.99），检查 seed 设置。

#### 9.4 分布式相关问题

##### 问题：模型同步（Model Update）卡住

**排查**：
1. 检查 Actor Train 和 Actor Infer 的 `device_mapping` 是否有交集
2. 检查 NCCL 通信组是否正确建立
3. 增大 `rpc_timeout`

##### 问题：多节点训练时某个节点挂掉

**排查**：
1. 检查各节点 GPU 状态：`nvidia-smi`
2. 检查 Ray 集群状态：`ray status`
3. 检查是否有 OOM Kill：`dmesg | grep -i oom`
4. 从最近的 checkpoint 恢复训练

##### 问题：Colocated 部署时 offload/reload 报错

**解决**：
- 确保 CPU 内存足够（offload 需要将模型参数暂存到 CPU）
- 检查 `offload_nccl` 配置是否正确
- 尝试切换到 disaggregated 部署（训练和推理使用不同 GPU）

### 十一、性能优化 Checklist

在正式开始大规模训练前，按以下清单逐项检查：

- [ ] **GPU 利用率**：训练阶段 GPU 利用率应 >80%，如果很低说明有瓶颈
- [ ] **Rollout 耗时**：确认 vLLM 的 `gpu_memory_utilization` 和 `max_model_len` 设置合理
- [ ] **数据加载**：`preprocessing_num_workers: 16` 确保数据预处理不成为瓶颈
- [ ] **梯度累积对齐**：确认 `gradient_accumulation_steps * dp_size * per_device_train_batch_size = rollout_batch_size * num_return_sequences_in_group`
- [ ] **显存余量**：训练时 GPU 显存占用不超过 90%
- [ ] **Checkpoint 存储**：确认 `output_dir` 有足够的磁盘空间
- [ ] **日志追踪**：确认 TensorBoard/SwanLab/WandB 正常记录指标
- [ ] **验证集**：确认 `eval_steps` 设置合理，验证集能正常运行
- [ ] **断点续训**：先跑几步，手动中断，测试 `resume_from_checkpoint` 是否正常
- [ ] **Infer 资源分配**：大模型（30B+）确保 infer 卡数充足，避免 generate 挤占
